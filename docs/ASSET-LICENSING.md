#🌈 Asset, Attribution, and Licensing Policy

##🌈 Core rule

Do not assume that every asset associated with Linux, Tux, SuperTux, SuperTuxKart, or an article about them shares one license.

Code, illustrations, character designs, models, textures, fonts, music, sound effects, logos, screenshots, and promotional images may have different authors, owners, and license terms. Verify each asset at the file or clearly defined asset-pack level before including it in a distributed build.

##🌈 Upstream game material

The creative direction includes possible characters and inspiration from:

- **SuperTux**
- **SuperTuxKart**

Before reusing assets, inspect the relevant upstream repositories and their current license and attribution files. Check individual asset metadata and notices, because an overall code license does not automatically cover every piece of artwork or media.

Where practical, contact upstream maintainers to explain the crossover concept, ask about attribution expectations, and discuss any assets whose license is unclear. Do not imply that either upstream project endorses this game without explicit permission.

##🌈 Tux artwork and the How-To Geek inspiration

The initial visual inspiration was a How-To Geek article image credited in the screenshot as **Lucas Gouveia / How-To Geek**. The image depicts a cybernetic, sunglasses-wearing Tux beside a classic Tux.

That article image must be treated as third-party material. Before reproducing, adapting, tracing, distributing, or using it as a production asset, identify the actual rights-holder and obtain permission or verify a license that expressly permits the intended use.

The project may independently develop its own classic and cybernetic Tux designs. Similarity of the general concept does not grant permission to copy the article's specific composition, rendering, character details, or other protected expression.

The project also discussed crediting **Larry Ewing** for the original Tux artwork and acknowledging **GIMP** in the artwork's history where appropriate. Before shipping any derivative of a particular Tux image, verify that image's source, applicable permission/license, and exact attribution requirements. Do not assume that a credit line alone grants permission. GIMP's role as an image-editing tool does not by itself make it the rights-holder of artwork created with it.

##🌈 Asset provenance ledger

Every third-party or externally sourced asset should have a record containing:

| Field | Description |
|---|---|
| Asset ID / path | Stable identifier and repository path |
| Description | What the asset contains and where it appears |
| Creator / rights-holder | Known author or owner |
| Source | Original source URL or repository and revision |
| License / permission | Exact license name, version, or written permission |
| Required attribution | Exact notice required by the license |
| Modifications | Whether the asset was modified and how |
| Commercial use | Whether the terms allow the planned use |
| Share-alike obligations | Any downstream licensing requirements |
| Review status | Pending, verified, restricted, or rejected |

Keep copies of license texts and permission records where redistribution terms allow it.

##🌈 Project-wide licensing is still undecided

The repository does not yet declare a project-wide license. A future decision must consider code, game data, original art, music, documentation, and contributions separately where necessary.

Do not add a blanket license header or claim that all project content is open-source until the scope and compatibility of the chosen licenses have been reviewed.

##🌈 Credits

Credits should be accurate, specific, and connected to the assets actually used. Preserve upstream notices and provide attribution in the locations required by each license, such as in-game credits, documentation, source files, or distribution packages.

Aspirational credit lists are not a substitute for provenance records.
